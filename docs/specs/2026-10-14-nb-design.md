# nb — knowledge base decentralizzata per team (design)

Data: 2026-10-14
Stato: bozza da approvare
Ambito: **Fase 1** (motore + MCP + hook + caricamento). La UI web è Fase 2 e avrà una spec propria.

## 1. Obiettivo

Un "NotebookLM decentralizzato" per un piccolo team di sviluppo.

- Le fonti (analisi, documentazione di progetti e applicativi, trascrizioni di videochiamate) vivono come `.md` in un **repo git condiviso** (hosting: Gitea).
- Ricerca e indicizzazione girano **in locale** su ogni PC, **solo CPU**, in modo veloce e leggero.
- Il "cervello" è **Claude Code** (abbonamento di ciascun membro): interroga il motore via MCP e risponde citando le fonti. Nessun LLM locale, nessuna API key, nessun server centrale.

### Criteri di successo

1. Dopo `git pull`, una domanda in Claude Code restituisce risposte con citazioni `percorso › sezione` senza ricalcolare embedding già calcolati da altri.
2. Ricerca su ~50k chunk in < 200 ms su un portatile senza GPU.
3. Un membro può caricare uno o più `.md` via Claude Code: il sistema propone collocazione, nome e frontmatter, e dopo conferma committa e pusha.
4. Nessun conflitto git possibile su file generati dal sistema; modifiche concorrenti sullo stesso `.md` vengono intercettate prima del commit.

### Fuori ambito

- Conversione PDF→md e trascrizione audio: fatte a mano dal team (es. PDF con Claude Code). Il motore indicizza **solo `.md`**.
- File originali (PDF, audio, video): **fuori dal repo**. Gli hook li bloccano.
- UI web (Fase 2). TUI: scartata (Claude Code è già la TUI).
- Controllo accessi per documento: chi ha il repo vede tutto.

## 2. Due repository distinti

| Repo | Contenuto | Chi lo modifica |
|---|---|---|
| **`nb`** (questo) | il tool: pacchetto Python, CLI, server MCP, hook, skill | sviluppatori del tool |
| **knowledge repo** | le fonti `.md` del team + `.nb/` + `.githooks/` | tutto il team |

`nb` si installa una volta per PC (`uv tool install`), poi si usa dentro qualsiasi knowledge repo.

## 3. Struttura del knowledge repo

```
knowledge-repo/
├── README.md              # convenzioni del team (lette da persone e da Claude)
├── CLAUDE.md              # regole di risposta e caricamento per Claude
├── .nb/
│   ├── config.toml        # modello embedding, parametri chunk  (committato)
│   ├── emb/               # vettori per hash di contenuto       (committati)
│   └── index.db           # indice SQLite locale                (gitignore)
├── .githooks/             # hook git condivisi                  (committati)
├── progetti/
│   └── <progetto>/
│       ├── analisi/
│       ├── documentazione/
│       └── call/          # trascrizioni: AAAA-MM-GG-titolo.md
└── generale/              # contenuti trasversali
```

### Metadati

Frontmatter YAML opzionale; se presente vince sul percorso.

```yaml
---
tipo: trascrizione        # analisi | documentazione | trascrizione | altro
progetto: portale-clienti
data: 2026-10-14
partecipanti: [Marco, Giulia]   # solo trascrizioni
---
```

Senza frontmatter: `progetto` e `tipo` derivano dal percorso (`progetti/<progetto>/<cartella>/`, con `call`→`trascrizione`); `data` dal nome file se nel formato `AAAA-MM-GG-…`.

Il percorso è **metadato e contesto**, non entra nel testo embeddato: spostare/rinominare file o cartelle non richiede ricalcoli.

## 4. Chunking

- **analisi / documentazione / altro**: split sui titoli markdown (`#`–`###`). Ogni chunk conserva il percorso titoli (`Spec auth › Login › SSO`), che **entra** nel testo embeddato (è interno al file, quindi stabile). Sezioni > `max_parole` (default 100) spezzate per paragrafi con overlap (default 20 parole). Il limite è basso perché il modello tronca a 128 token.
- **trascrizione**: finestre di ~`max_parole` parole che non tagliano a metà battuta; conserva speaker e timestamp se presenti (`**Marco** [00:12:03]:` o `Marco:`).

Ogni chunk registra: percorso file, percorso titoli, righe inizio/fine, metadati del file, hash.

## 5. Embedding committati, indirizzati per contenuto

- Modello: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (384 dim, 0,22 GB, ONNX via `fastembed`, CPU, verificato tra i modelli supportati), fissato in `.nb/config.toml` con `model_id`.
- Chiave: `hash = sha256(model_id + "\n" + testo_chunk_embeddato)`.
- File: `.nb/emb/<hash[:2]>/<hash>.bin` — 384 × float16 = 768 byte.
- Proprietà:
  - immutabili, nome unico → **nessun conflitto di merge**;
  - testo uguale → stesso file → dedup gratuita;
  - calcolati **una volta nel team** (da chi carica/committa), gli altri li riusano.
- Vettori mancanti (qualcuno ha committato senza hook): calcolati localmente alla prima indicizzazione, aggiunti al commit successivo.
- Vettori orfani: rimossi da `nb gc`.
- Cambio modello: `nb reembed`, operazione esplicita fatta da una persona. Se `model_id` della config non corrisponde a quello dell'indice → errore chiaro.
- **Regola**: nessun file condiviso mutabile generato dal sistema (niente manifest/indici comuni).

## 6. Componenti del pacchetto `nb`

Moduli piccoli, una responsabilità ciascuno.

| Modulo | Responsabilità | Dipende da |
|---|---|---|
| `config` | legge/valida `.nb/config.toml` | — |
| `fonti` | trova i `.md`, estrae metadati (frontmatter + percorso) | config |
| `regole` | validazione condivisa: percorsi ammessi, naming, frontmatter, binari, marcatori conflitto, segreti | config |
| `chunker` | split per titoli / per battute | fonti |
| `embedder` | wrapper `fastembed`, batch, `model_id` | config |
| `vettori` | lettura/scrittura `emb/`, mancanti, `gc` | embedder |
| `indice` | SQLite: tabelle file/chunk (vettori come BLOB), FTS5; sync incrementale (mtime + hash); matrice vettori in memoria (numpy, ricerca esatta) | chunker, vettori |
| `ricerca` | ibrida BM25 + vettoriale, fusione RRF, filtri (progetto, tipo, data) | indice |
| `guardia` | file in staging modificati sul remoto (`git log HEAD..@{u} -- <file>`) | git |
| `caricamento` | similari/duplicati, applicazione piano, commit atomico, push | regole, ricerca, guardia |
| `mcp` | server MCP: adattatore sottile | ricerca, fonti, caricamento |
| `cli` | `nb init / index / search / check / status / sync / gc / reembed / hook <nome>` | tutti |

`ricerca`, `fonti` e `caricamento` sono l'API interna: MCP, CLI e la futura UI sono solo adattatori.

**Dipendenze**: Python 3.12 (onnxruntime), `fastembed`, `numpy`, `mcp` (SDK ufficiale), `pyyaml`, `typer`. Git invocato via subprocess.

## 7. Tool MCP

| Tool | Input | Output |
|---|---|---|
| `cerca` | `query`, `progetto?`, `tipo?`, `da?`, `a?`, `k=8` | chunk: testo, `percorso › titoli`, righe, metadati, punteggio |
| `leggi_fonte` | `percorso`, `sezione?` | documento intero o sezione |
| `elenca_fonti` | `progetto?`, `tipo?` | albero con metadati |
| `stato` | — | indice aggiornato?, vettori mancanti, file obsoleti rispetto al remoto, avvisi frontmatter |
| `proponi_collocazione` | `file[]` (percorsi locali o contenuto) | per file: 5 documenti più simili con cartella, possibili duplicati (cos > 0,95), progetti esistenti, convenzioni |
| `carica_fonti` | `piano[]` (sorgente, destinazione, frontmatter, `aggiorna?`), `messaggio?`, `push=true` | commit hash o errore; nessuno stato parziale |

**Auto-sync**: all'avvio del server e prima di ogni `cerca`, sync incrementale dell'indice. Mai `nb index` manuale nel flusso normale.

### `carica_fonti` — sequenza

1. Valida ogni voce con `regole` (stesse regole degli hook). Errore → rifiuto con motivazione, nulla scritto.
2. Rifiuta se c'è già qualcosa in staging o se i percorsi di destinazione hanno modifiche locali non committate.
3. Registra `start = HEAD`; `git pull --rebase --autostash`.
4. Scrive i file, calcola vettori, esegue `guardia`.
5. `git add` dei soli file del lotto + vettori; un unico commit; `push` se richiesto.
6. Errore prima del commit → ripristina i file del lotto (`git restore` per i modificati, rimozione per i nuovi). Errore dopo il commit (push rifiutato) → `git reset --mixed <commit del pull>` e ripristino come sopra. Mai `reset --hard`: le altre modifiche locali dell'utente non vengono toccate. Errore riportato con causa.

## 8. Regole per Claude (`CLAUDE.md` del knowledge repo + skill)

**Risposta**
- Cita sempre `percorso › sezione`; per le trascrizioni data della call e chi ha parlato.
- Se l'informazione non è nelle fonti: "non presente nelle fonti", mai inventare.

**Caricamento (skill `/nb-carica`, versionata nel knowledge repo)**
- Usa sempre `proponi_collocazione` prima di decidere.
- Preferisci la cartella dei documenti più simili.
- Duplicato probabile → proponi di aggiornare il file esistente.
- Deduci il frontmatter dal contenuto (tipo, progetto, data, partecipanti).
- Nomi: slug minuscolo con trattini; call `AAAA-MM-GG-titolo.md`.
- Mostra il piano in tabella e **attendi conferma** prima di `carica_fonti`. Nuovo progetto/cartella → conferma esplicita separata.

## 9. Hook git

In `.githooks/` del knowledge repo, attivati da `nb init` (`git config core.hooksPath .githooks`). Ogni hook è un wrapper di una riga: `nb hook <nome>`.

### `pre-commit`
| Controllo | Esito |
|---|---|
| Guardia: file in staging modificato sul remoto | **blocco** con commit, autore, età e comando (`git pull --rebase`) |
| Marcatori di conflitto `<<<<<<<` / `>>>>>>>` in `.md` | **blocco** |
| Frontmatter YAML non valido | **blocco** |
| `tipo` non ammesso | **blocco** |
| Call non nel formato `AAAA-MM-GG-titolo.md` | **blocco** |
| File fuori dalla struttura prevista | avviso |
| Binari (pdf, audio, video, immagini) o file > 5 MB | **blocco** |
| Segreti: pattern certi (chiavi private, token noti) | **blocco** |
| Segreti: pattern probabili (`password:` ecc.) | avviso |
| Vettori mancanti | calcolati e aggiunti al commit |

Guardia: `git fetch` con timeout 3 s. Fetch fallito / offline / branch senza upstream → avviso, nessun blocco. Blocca solo i file effettivamente modificati sul remoto, non l'essere indietro in generale.

### `pre-push`
- Guardia ripetuta su tutti i file dei commit da pushare.
- Coerenza: ogni `.md` pushato ha tutti i suoi vettori → altrimenti blocco con comando suggerito.

### `post-merge`, `post-checkout`, `post-rewrite`
- Sync incrementale dell'indice in background.
- Riepilogo: fonti nuove/modificate per progetto.

### Hook Claude Code (`PreToolUse` su Edit/Write)
Nel `.claude/settings.json` del knowledge repo: prima di modificare un `.md` esegue `nb check <file>`; se obsoleto avvisa e propone il pull.

### Limiti
Gli hook client si aggirano con `--no-verify`: proteggono dagli errori, non dalla malafede. Lato server (Gitea): branch protection su `main` — niente force push né cancellazione. Documentato nel README del knowledge repo.

## 10. Flusso dati

1. **Caricare**: Claude Code → `proponi_collocazione` → piano → conferma → `carica_fonti` → commit + push (vettori inclusi).
2. **Aggiornarsi**: `git pull` (o `nb sync` = pull --rebase + index + push vettori mancanti) → `post-merge` sincronizza l'indice.
3. **Interrogare**: domanda → `cerca` (ibrida + filtri) → eventuale `leggi_fonte` → risposta con citazioni.

## 11. Gestione errori

| Situazione | Comportamento |
|---|---|
| Vettori mancanti | calcolati in locale, avviso |
| `model_id` diverso tra config e indice | indice ricostruito da `emb/` (il cambio modello si fa con `nb reembed`) |
| Frontmatter rotto (file già nel repo) | indicizzato con metadati da percorso, avviso in `stato` |
| `index.db` corrotto o schema vecchio | cancellato e ricostruito automaticamente |
| Fetch fallito nella guardia | avviso, nessun blocco |
| Conflitto/push rifiutato in `carica_fonti` | rollback del lotto, errore riportato |

## 12. Test

- **Unitari**: chunker (titoli, sezioni lunghe, trascrizioni con/senza timestamp), estrazione metadati, naming hash, `regole` (ogni regola, caso ok e ko).
- **Integrazione**: knowledge repo di fixture (md + emb) → `index` → `cerca` con risultati e filtri attesi; sync incrementale (aggiunta, modifica, rimozione, spostamento senza ricalcolo).
- **Guardia e hook**: repo bare + due cloni; modifica concorrente → blocco; file diversi → passa; offline → avviso.
- **Caricamento**: piano valido → un commit; piano invalido → nulla scritto; push rifiutato → rollback.
- **MCP**: chiamate ai tool tramite client di test dell'SDK.
- **Prestazioni**: 50k chunk sintetici, ricerca < 200 ms.
